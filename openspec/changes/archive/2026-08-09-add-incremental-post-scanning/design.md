## Context

当前 `run_once()` 先取得作者的全部分页 URL，再逐页请求帖子摘要；目录存在判断发生在分页请求之后，因此只能减少详情和文件请求，不能减少历史分页请求。帖子目录同时被当作完成标志，导致部分下载后已创建目录的帖子也可能被永久跳过。

FANBOX 列表允许帖子置顶和取消置顶，单一帖子游标或页码不能作为可靠的完成事实。调度器保证同一时间只有一轮任务，因此状态保存不需要跨进程锁。

## Goals / Non-Goals

**Goals:**

- 使用帖子 ID 状态清单作为完成事实，不依赖帖子顺序或页码稳定性。
- 普通运行仅请求足够的近期分页，完整扫描只用于首次初始化或状态重建。
- 在文件下载失败、进程中断和容器重建后安全恢复。
- 继续只持久化下载目录，不增加数据库或第三方依赖。
- 保持旧版本已有帖子目录在升级后不会被全部重新下载。

**Non-Goals:**

- 不检测已完成帖子的内容编辑或新增附件。
- 不检测帖子目录内单个文件被手工删除；现有的整目录删除重下方式继续保留。
- 不提供数据库、跨容器共享状态或并行下载协调。
- 不自动发现快速扫描边界之外的历史解锁或回填帖子；需要操作者删除状态以触发完整重建。

## Decisions

### 1. 在下载目录保存单个版本化 JSON 文件

状态文件使用 `<download-directory>/.fanbox-state.json`，结构保持最小：

```json
{
  "version": 1,
  "creators": {
    "creator-id": {
      "initialized": true,
      "posts": {
        "12345678": "downloaded",
        "12345679": "empty",
        "12345680": "restricted"
      }
    }
  }
}
```

三个状态分别表示：文件完整处理、帖子无文件、当前访问受限。未记录的帖子始终视为待处理；不保存失败状态或错误文本。

选择 JSON 而不是 SQLite，是因为状态只需按作者和 ID 做集合查询，单进程运行且规模有限。加载后直接使用字典，不需要新依赖或数据库迁移。

### 2. 状态文件是完成事实，文件存在只负责下载幂等

帖子只有在全部资源下载成功后才写入 `downloaded`。任何文件失败时不写入帖子状态；下一轮重新读取详情，现有 `dl()` 继续跳过已经存在的文件并补齐缺失文件。

成功读取但没有资源的帖子写入 `empty`。列表明确显示受限的帖子写入 `restricted`，普通运行可跳过重复详情请求；近期列表显示其已解除限制或状态被重建时重新处理。

这取代“帖子目录存在即完成”的运行时判断，但文件级存在检查继续保留。

### 3. 仅在没有有效状态时从旧目录迁移

第一次升级或状态不可用时，扫描每个作者目录，提取符合 `<post-id>-<title>` 格式的 ID 并初始化为 `downloaded`，随后执行完整分页扫描以补充无文件、受限和尚未下载的帖子。

一旦有效状态文件存在，不再用未登记的目录推断完成状态。这样进程在创建目录后、写入完成状态前中断时，下一轮仍会重试该帖子。

加载状态时同时检查标记为 `downloaded` 的帖子目录。目录整体缺失的 ID 从完成状态中移除，并在分页扫描前直接按 ID 重试，从而保留 README 已有的“删除帖子目录后重新下载”行为。

### 4. 普通扫描使用已知页面重叠，而不是单一游标

普通运行仍按 FANBOX 返回顺序从最近分页开始。每个帖子独立按 ID 查询状态：

- 未知 ID：处理并在成功后记录；
- `restricted` 且当前已解除限制：重新处理；
- 其他已知 ID：跳过。

页面处理结束后，如果其中每个帖子都已有状态记录，则记为一个已知页面；否则重置连续计数。达到连续两个已知页面时停止该作者的普通扫描。

置顶和取消置顶只会移动已有 ID，不会改变状态判断。两个页面的重叠是减少常规 API 请求的启发式边界；边界之外的历史变化不会自动触发扫描。

备选方案是每次完整遍历，但它不能解决原始性能问题；单一游标则会直接依赖排序，故不采用。

### 5. 完整扫描仅用于初始化和状态重建

每个作者保存 `initialized` 标志。以下情况忽略快速扫描停止条件并读取全部分页：

- 没有有效状态或没有该作者记录；
- 作者的 `initialized` 不是 true；
- 状态版本或内容无法验证。

创建作者状态时先保存 `initialized: false`。只有全部分页成功读取，且本轮发现的所有可处理帖子均成功完成后，才写入 `initialized: true`。初始化失败时，下一次计划任务继续完整扫描。

有效状态不会因为经过固定时间而自动完整扫描。需要发现快速扫描边界之外的历史解锁或回填帖子时，操作者删除状态文件；已有帖子目录会在迁移阶段重新识别。

### 6. 每次帖子状态变化后原子保存

状态序列化到下载目录中的临时文件，成功关闭后使用 `os.replace()` 替换正式文件。临时文件和正式文件位于同一文件系统，保证替换原子性。

每个帖子完成、受限状态变化、目录缺失修复以及作者初始化完成后立即保存。新帖子数量通常很少，相比 API 和文件下载成本，重复写入小型 JSON 可忽略，并能减少进程中断时的重复工作。

状态无法解析或版本不支持时打印警告、忽略该状态并完整重建；已有下载文件不删除。

## Risks / Trade-offs

- [普通扫描不会发现边界之外的历史解锁或回填帖子] → 文档说明删除状态文件可触发完整重建。
- [两个已知页面是启发式阈值] → 帖子 ID 清单保证已发现帖子的幂等性；不承诺自动覆盖边界之外的历史变化。
- [JSON 随帖子数量线性增长] → 每帖仅保存 ID 和短状态字符串；在预期个人下载规模内远小于下载内容，达到实际瓶颈后再考虑 SQLite。
- [状态文件损坏会触发昂贵的完整扫描] → 原子替换降低损坏概率，并从现有目录迁移以避免重新下载。
- [旧版本遗留的部分帖子目录无法与完整目录区分] → 首次迁移沿用旧版本“目录即完成”的兼容语义；用户可删除可疑目录后重新处理。

## Migration Plan

1. 升级版本首次启动时发现没有状态文件，扫描现有作者目录并建立初始 ID 状态。
2. 执行一次完整分页扫描，记录无文件、受限和新增帖子，并在成功后把作者标记为已初始化。
3. 后续计划任务进入快速扫描，除非状态被删除、损坏或初始化未完成。状态继续随已有下载 volume 保存。
4. 回滚到旧版本时，旧程序忽略隐藏 JSON 文件并继续使用原有目录判断；下载文件无需迁移。
